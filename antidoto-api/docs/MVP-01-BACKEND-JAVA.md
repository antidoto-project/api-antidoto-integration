## 1. Objetivo
Uma API REST simples que:
1. autentica com JWT (perfis `CIDADAO` e `GESTOR`);
2. devolve as **unidades próximas com soro compatível** (público);
3. registra **ocorrências**, calcula a **urgência** e gera um **resumo de pré-atendimento por IA** de forma **assíncrona** (RabbitMQ + Spring AI);
4. faz o **CRUD de avistamentos** (usado pelo app) e o **CRUD de unidades** (perfil GESTOR, via Swagger).

### Como isso cobre a nota de Java Advanced
| Critério | Pts | Onde está |
|---|---|---|
| API REST: ≥ 3 entidades relacionadas, CRUD JPA, paginação | 20 | `Usuario` 1–N `Ocorrencia` N–1 `UnidadeSaude`; `Usuario` 1–N `Avistamento`; CRUD de `Avistamento` e `UnidadeSaude`; listas paginadas |
| Bean Validation + `@RestControllerAdvice` | 10 | DTOs com `@NotNull`, `@Email`, `@Size`, `@DecimalMin/Max`; handler global (§7) |
| Spring Security + JWT com 2 papéis | 20 | `CIDADAO` e `GESTOR` (§5) |
| Spring AI integrado ao fluxo | 20 | Resumo de pré-atendimento gerado a cada ocorrência (§8) |
| Arquitetura distribuída (opção **A**) | 20 | Evento `ocorrencia.criada` publicado no RabbitMQ e consumido de forma assíncrona (§9) |
| Swagger + README + consumo pelo Mobile | 10 | springdoc + README (§12) + o app consumindo |

```
├── repository/    (interfaces Spring Data JPA)
```

- Código em português (o mesmo padrão do time); nomes reservados do framework ficam como são.
- **Controller** só recebe, valida (`@Valid`), chama o service e devolve o DTO. **Regra de negócio fica no service.**
- **Entidades nunca saem do service**: sempre converter para um DTO (`record`).
- Injeção por **construtor**.
- `Clock` injetável (um bean) nas regras de tempo (3 h, 72 h), para os testes conseguirem controlar o horário.

### 4.2 DDL (`src/main/resources/db/migration/V1__criar_tabelas.sql`, compatível com Oracle e H2 em modo Oracle)
```sql
CREATE TABLE usuarios (
  id          NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  nome        VARCHAR2(120) NOT NULL,
  email       VARCHAR2(160) NOT NULL,
  senha_hash  VARCHAR2(100) NOT NULL,
  telefone    VARCHAR2(11),
  perfil      VARCHAR2(10)  NOT NULL,
  criado_em   TIMESTAMP     NOT NULL,
  CONSTRAINT uk_usuarios_email UNIQUE (email),
  CONSTRAINT ck_usuarios_perfil CHECK (perfil IN ('CIDADAO','GESTOR'))
);

CREATE TABLE unidades_saude (
  id            NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  nome          VARCHAR2(160) NOT NULL,
  tipo          VARCHAR2(10)  NOT NULL,
  endereco      VARCHAR2(250) NOT NULL,
  telefone      VARCHAR2(11)  NOT NULL,
  latitude      NUMBER(9,6)   NOT NULL,
  longitude     NUMBER(9,6)   NOT NULL,
  atende_24h    NUMBER(1)     NOT NULL,
  ativa         NUMBER(1)     DEFAULT 1 NOT NULL,
  atualizado_em TIMESTAMP     NOT NULL,
  CONSTRAINT ck_unidades_tipo CHECK (tipo IN ('HOSPITAL','UPA','UBS'))
);

CREATE TABLE unidade_soros (
  unidade_id NUMBER(19)   NOT NULL,
  soro       VARCHAR2(20) NOT NULL,
  CONSTRAINT pk_unidade_soros PRIMARY KEY (unidade_id, soro),
  CONSTRAINT fk_unidade_soros FOREIGN KEY (unidade_id) REFERENCES unidades_saude(id)
);

CREATE TABLE ocorrencias (
  id             NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  usuario_id     NUMBER(19)     NOT NULL,
  unidade_id     NUMBER(19),
  tipo_animal    VARCHAR2(10)   NOT NULL,
  faixa_etaria   VARCHAR2(10)   NOT NULL,
  hora_picada    TIMESTAMP      NOT NULL,
  latitude       NUMBER(9,6)    NOT NULL,
  longitude      NUMBER(9,6)    NOT NULL,
  urgencia       VARCHAR2(10)   NOT NULL,
  motivos        VARCHAR2(500)  NOT NULL,
  status_resumo  VARCHAR2(15)   NOT NULL,
  resumo         VARCHAR2(2000),
  criado_em      TIMESTAMP      NOT NULL,
  CONSTRAINT fk_ocorrencias_usuario FOREIGN KEY (usuario_id) REFERENCES usuarios(id),
  CONSTRAINT fk_ocorrencias_unidade FOREIGN KEY (unidade_id) REFERENCES unidades_saude(id),
  CONSTRAINT ck_ocorrencias_urgencia CHECK (urgencia IN ('EMERGENCIA','ALTA','MODERADA')),
  CONSTRAINT ck_ocorrencias_status CHECK (status_resumo IN ('PENDENTE','PRONTO','MODELO_PADRAO'))
);

CREATE TABLE ocorrencia_sintomas (
  ocorrencia_id NUMBER(19)   NOT NULL,
  sintoma       VARCHAR2(30) NOT NULL,
  CONSTRAINT pk_ocorrencia_sintomas PRIMARY KEY (ocorrencia_id, sintoma),
  CONSTRAINT fk_ocorrencia_sintomas FOREIGN KEY (ocorrencia_id) REFERENCES ocorrencias(id)
);

CREATE TABLE avistamentos (
  id            NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  usuario_id    NUMBER(19)    NOT NULL,
  tipo_animal   VARCHAR2(10)  NOT NULL,
  local_avist   VARCHAR2(15)  NOT NULL,
  latitude      NUMBER(9,6)   NOT NULL,
  longitude     NUMBER(9,6)   NOT NULL,
  data_hora     TIMESTAMP     NOT NULL,
  observacao    VARCHAR2(500),
  criado_em     TIMESTAMP     NOT NULL,
  atualizado_em TIMESTAMP,
  CONSTRAINT fk_avistamentos_usuario FOREIGN KEY (usuario_id) REFERENCES usuarios(id)
);
CREATE INDEX ix_avistamentos_usuario ON avistamentos (usuario_id, criado_em);
CREATE INDEX ix_ocorrencias_usuario ON ocorrencias (usuario_id, criado_em);
```
> `local_avist` é o nome da coluna para evitar a palavra reservada `LOCAL`; no JSON o campo continua `local`.
> `GENERATED BY DEFAULT AS IDENTITY` funciona no Oracle 12c+ e no H2.
> Nunca usar `ddl-auto=update` (o schema é do Flyway; usar `ddl-auto=none`).

## 5. Segurança
- JWT **HS256**, segredo em `JWT_SECRET` (base64, ≥ 32 bytes), **validade de 24 h**, sem refresh token (simplificação do MVP).
- Claims: `sub` (id do usuário), `email`, `perfil`.
- Senha com **BCrypt**. Cadastro: ≥ 8 caracteres, com letra e número. E-mail com `trim().toLowerCase()`.
- Login inválido ⇒ **401** com a mensagem genérica "E-mail ou senha incorretos".
- Stateless, CSRF desabilitado, filtro JWT antes do `UsernamePasswordAuthenticationFilter`. 401 e 403 respondem no formato `Erro` (§7).

| Rota | Público | CIDADAO | GESTOR |
|---|:-:|:-:|:-:|
| `POST /api/auth/**` | ✔ | | |
| `GET /api/unidades`, `/api/unidades/proximas`, `/api/unidades/{id}` | ✔ | ✔ | ✔ |
| `POST/PUT/DELETE /api/unidades/**` | | | ✔ |
| `/api/usuarios/me` | | ✔ | ✔ |
| `/api/ocorrencias`, `/minhas`, `/{id}` | | ✔ (só as suas) | ✔ (só as suas) |
| `GET /api/ocorrencias/unidade/{id}` | | | ✔ |
| `/api/avistamentos/**` | | ✔ (só os seus) | ✔ (só os seus) |
| `/actuator/health`, `/swagger-ui.html`, `/swagger-ui/**`, `/v3/api-docs/**` | ✔ | | |

- Recurso de **outro usuário ⇒ 404** (não 403).
- CORS: origens vindas de `CORS_ORIGENS` (Expo Web/Swagger). Nunca `*` em prod.

## 6. Regras por endpoint

### 6.1 Auth / Usuário
- `POST /api/auth/cadastro`: cria o usuário com perfil `CIDADAO` e devolve **201** + `AuthResponse`. E-mail existente ⇒ **409**.
- `POST /api/auth/login` ⇒ 200 + `AuthResponse`.
- `GET/PUT /api/usuarios/me`: o PUT altera só `nome` e `telefone`.

### 6.2 Unidades
- `GET /api/unidades`: só as ativas, ordenadas por nome, paginadas.
- `GET /api/unidades/proximas`: aplicar **RN-S1…RN-S4** (`MVP-00` §4.4) com `CompatibilidadeSoroService` + Haversine (raio da Terra = 6371 km); `distanciaKm` arredondado para 1 casa decimal.
  Como o volume é pequeno, carregar as unidades ativas e filtrar/ordenar em memória.
- `POST/PUT` (GESTOR): validar a latitude (−34 a 6), a longitude (−74 a −34) e o telefone (10–11 dígitos). `soros` substitui a lista inteira.
- `DELETE` (GESTOR): **exclusão lógica** (`ativa = false`) ⇒ **204**.

### 6.3 Ocorrências
**`POST /api/ocorrencias`** (logado):
1. Validar: **RN-G4** (`horaPicada` nem no futuro além de 5 min, nem anterior a 72 h) ⇒ **400** no campo `horaPicada`.
2. Se `unidadeId` vier, a unidade precisa existir e estar ativa ⇒ senão **404**.
3. `UrgenciaService.calcular(tipoAnimal, faixaEtaria, sintomas, horaPicada, agora)` ⇒ `urgencia` + `motivos` (**RN-U**, `MVP-00` §4.3).
4. Salvar com `statusResumo = PENDENTE`.
5. **Depois do commit**, publicar `OcorrenciaCriadaEvento { ocorrenciaId }` (§9).
6. Responder **201** com `ligar192 = (urgencia == EMERGENCIA)`, `aviso` = "Procure atendimento médico imediatamente." e `avisoResumo` = "Resumo gerado por IA. Não substitui avaliação profissional."

- `GET /api/ocorrencias/minhas`: do usuário logado, `criadoEm DESC`, paginado.
- `GET /api/ocorrencias/{id}`: só o dono (senão **404**). É o endpoint que o app consulta até o resumo ficar pronto.
- `DELETE /api/ocorrencias/{id}`: só o dono ⇒ **204**.
- `GET /api/ocorrencias/unidade/{unidadeId}` (GESTOR): ocorrências com aquela unidade de destino, `criadoEm DESC`.

### 6.4 Avistamentos (o CRUD do app)
- `POST`: `dataHora` não pode estar no futuro (+5 min de tolerância) ⇒ **400**. Dono = usuário logado ⇒ **201**.
- `GET /meus`: do usuário logado, `criadoEm DESC`, paginado.
- `GET/PUT/DELETE /{id}`: só o dono (**RN-G5**); de outro usuário ou inexistente ⇒ **404**. O PUT atualiza `atualizadoEm`. O DELETE é físico ⇒ **204**.

### 6.5 Paginação
Parâmetros `pagina` (padrão 0) e `tamanho` (padrão 20, máx. 50). Resposta **sempre** no formato:
```json
{ "conteudo": [ ... ], "pagina": 0, "tamanho": 20, "totalElementos": 3, "totalPaginas": 1 }
```
Não devolver o `Page` do Spring diretamente: criar um `record PaginaResponse<T>`.

Formato único (o app lê esse formato):

```json
{
  "status": 400,
  "erro": "Dados inválidos",

```
| Situação | Status |
|---|---|

| Sem token, token inválido ou login errado | 401 |
| Perfil sem permissão | 403 |
| Não encontrado ou não é seu | 404 |
| E-mail já cadastrado | 409 |
| Erro inesperado | 500 (mensagem genérica, sem stack trace) |

Mensagens **em português**, prontas para aparecer na tela.

## 8. Spring AI — resumo de pré-atendimento
**Onde entra no fluxo:** cada ocorrência registrada ganha um resumo objetivo que o cidadão mostra na recepção da unidade.
Não é um chat solto: é gerado automaticamente, a partir dos dados estruturados.

`ResumoIaService.gerar(Ocorrencia)`:
- Monta **somente** com: tipo de animal, faixa etária, sintomas (texto em pt-BR, marcando os sinais de alerta), hora da picada e minutos decorridos, urgência + motivos e o nome da unidade de destino.
  **Proibido** mandar nome, e-mail, telefone, id do usuário ou coordenadas.
- `ChatClient` com este *system prompt*:
  ```
  Você gera um RESUMO DE PRÉ-ATENDIMENTO curto e objetivo para a equipe de uma unidade de saúde.
  Use SOMENTE os dados fornecidos. Não invente informações.
  NUNCA sugira tratamento, medicamento ou dose.
  Formato: no máximo 6 linhas, em português:
  1) Animal  2) Hora da picada e tempo decorrido  3) Faixa etária
  4) Sintomas (destaque os sinais de alerta)  5) Urgência calculada e motivos  6) Unidade de destino
  ```
- `temperature 0.2`, `max-tokens 300`, *timeout* de 6 s (`CompletableFuture...orTimeout`).
- **Validação da resposta:** vazia, maior que 1.200 caracteres ou contendo `dose`, `mg`, `ml`, `ampola` ou `medicamento` ⇒ descartar.
- **Fallback (`ResumoModeloPadrao`)**: IA desligada (`IA_HABILITADA=false`), erro, timeout ou resposta descartada ⇒ texto montado por template, com `statusResumo = MODELO_PADRAO`. Exemplo:
  ```
  PRÉ-ATENDIMENTO — SOS Peçonha
  Animal: Escorpião · Faixa etária: criança
  Picada: 22:15 (há 25 min)
  Sintomas: vômitos repetidos (ALERTA)
  Urgência: EMERGÊNCIA — Sinal de alerta; Escorpião em criança
  Destino: Hospital Exemplo Centro
  ```
- Sucesso ⇒ `statusResumo = PRONTO`.
- **Não logar** o prompt nem a resposta; logar só o id, o status e a latência.

Configuração do Groq:
```yaml
spring:
  ai:
    openai:
      api-key: ${GROQ_API_KEY:desligado}
      base-url: https://api.groq.com/openai
      chat.options:
        model: ${IA_MODELO:llama-3.3-70b-versatile}   # ver os modelos atuais em console.groq.com
        temperature: 0.2
    model:                 # o Groq só tem chat: desligar os outros modelos auto-configurados
      embedding: none
      image: none
      audio.speech: none
      audio.transcription: none
      moderation: none
```
> Os nomes das propriedades `spring.ai.model.*` podem variar entre versões 1.x. Se o startup reclamar de um bean de embedding, ajuste conforme a documentação da versão.

## 9. RabbitMQ — processamento assíncrono (opção A do edital)
- Fila **`sospeconha.ocorrencia.criada`** (durable), com DLQ **`sospeconha.ocorrencia.criada.dlq`** (3 tentativas).
- **Produtor:** `OcorrenciaPublisher` publica `{ "ocorrenciaId": 10, "criadoEm": "..." }` (JSON, `Jackson2JsonMessageConverter`)
  **após o commit** (`@TransactionalEventListener(phase = AFTER_COMMIT)`).
- **Consumidor:** `ResumoOcorrenciaConsumer` (`@RabbitListener`) ⇒ carrega a ocorrência ⇒ `ResumoIaService.gerar` ⇒ salva `resumo` + `statusResumo`.
  Se a ocorrência já não estiver `PENDENTE`, ignora (**idempotente**).
- **Sem RabbitMQ** (`MENSAGERIA_HABILITADA=false`, perfis `dev`/`test`): o publisher chama o mesmo processamento com `@Async`.
  O sistema funciona igual; a **demonstração e o deploy usam o RabbitMQ**.
- Na nuvem: RabbitMQ gerenciado gratuito (ex.: CloudAMQP) ou um container na Azure (decisão de quem faz a cloud).

## 11. Testes (rodam no CI com `mvn verify`)
**Unitários (sem Spring):**
- `UrgenciaServiceTest`: os **10 casos** da tabela do `MVP-00` §4.3 (parametrizado), com `Clock` fixo.
- `CompatibilidadeSoroServiceTest`: cada linha da RN-S, incluindo NAO_SEI e ABELHA.
- `HaversineTest`: a distância entre dois pontos conhecidos (ex.: Praça da Sé × Av. Paulista ≈ 2,5–3 km, com tolerância).
- `ResumoIaServiceTest`: o timeout cai no `MODELO_PADRAO`; uma resposta com "dose" cai no `MODELO_PADRAO`; o texto enviado à IA **não** contém o e-mail nem o nome.

**Integração (`@SpringBootTest` + MockMvc + H2):**
- Cadastro → login → `/usuarios/me`; e-mail repetido ⇒ 409; senha errada ⇒ 401.
- Avistamentos: CRUD completo; o de outro usuário ⇒ 404; sem token ⇒ 401.
- Unidades: CIDADAO em `POST /api/unidades` ⇒ 403; GESTOR ⇒ 201; `GET /proximas` sem login ⇒ 200.
- Ocorrência: `POST` ⇒ 201 com `PENDENTE`; depois o processamento (`@Async` no teste) deixa `MODELO_PADRAO`; `horaPicada` no futuro ⇒ 400.

## 13. ❌ Não fazer
1. Commitar segredos (`JWT_SECRET`, senha do banco, `GROQ_API_KEY`) ou o `.env`.
2. Devolver entidade JPA ou o `Page` do Spring diretamente.
3. Usar `ddl-auto=update/create`.
4. Colocar regra de negócio no controller.
5. Deixar a IA decidir a urgência ou falar de dose/remédio; fazer um "chat genérico".
